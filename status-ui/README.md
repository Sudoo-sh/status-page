# status-ui

A redesigned status page for status.sudoo.sh. Review and preview only: nothing here is wired into the live site.

## Safety

- Everything lives in `status-ui/`. Nothing under `assets/`, `.github/workflows/`, `.upptimerc.yml`, `history/`, `api/` or `graphs/` is changed.
- `.github/workflows/site.yml` (Static Site CI, generated by Upptime) runs on a push to **any branch** that changes `assets/**`, checks out that branch and deploys to `gh-pages`. A preview branch must therefore never touch `assets/**`. This one does not.
- Moving the built page into `assets/` (the step that would go live) is a separate decision and is not part of this patch.
- `proposals/status-ui-build.yml` is a disabled, review-only proposal, outside `.github/workflows/`, so nothing runs it.

## Preview

```
node status-ui/build.mjs --out /tmp/preview --data fixture --fixture sample   # illustrative states, "Sample data" banner
node status-ui/build.mjs --out /tmp/preview --data fixture --fixture calm
node status-ui/build.mjs --out /tmp/preview --data fixture --fixture unknown
node status-ui/build.mjs --out /tmp/preview --data live                       # reads this checkout's history/ and the public issues API
python3 -m http.server -d /tmp/preview 8080
```

`--data live` needs the full git history (`git fetch --unshallow`) because the response-time lines come from the commit history of `history/<slug>.yml`. Node 18 or newer, no dependencies. Tests: `node --test status-ui/test/logic.test.mjs`.

Fixtures are examples, shown with a permanent "Sample data" banner. They are never the default.

## What the page shows, and what it does not claim

- A per-service state from what the monitor recorded: Working, Slow (response over 2000 ms, the rule already in status-page#2), Check failing (the monitor recorded status down; the HTTP code is shown and no cause is claimed), Check needs attention (down with a recorded redirect, 401 or 403 where another code was expected; code and expected codes shown, no cause claimed), Unknown (no recorded update, or an update older than `STALE_AFTER_MIN` in `src/config.js`, currently 60 min, a page setting and not an Upptime value).
- The headline stays at the level of check evidence: "Some checks are failing", "Some checks need attention", "Some checks are out of date", "No recorded observations" (no service has a recorded update), "Some systems are slow", and "All systems working" only when every service has a recent recorded update and none is slow, failing or needs attention. The page shows what the monitor recorded in repository files at build time, not a live probe.
- "Last recorded update" comes from the `lastUpdated` field in `history/<slug>.yml`. What exactly Upptime writes there on each check is not confirmed, so the page does not call it "last check".
- Uptime for 24 h, 7 d, 30 d and since monitoring began comes from `history/summary.json`; next to each figure the row says how many days of data back it when that is less than the range. The 90 d choice is hidden until the data supports it: Upptime gives no 90-day figure and the files do not show complete daily coverage. It is never taken from the year value.
- The 90 daily blocks use `dailyMinutesDown`. Days before monitoring began are empty "No data". A day without an entry is "No downtime recorded", not a claim of 100%.
- Response-time lines are "recorded samples" from commits of `history/<slug>.yml`. A commit is not a check, so nothing is resampled or filled and no check count is claimed.
- Incidents use issues labelled `status` (created/closed times, title, service from a slug label if present). Maintenance uses issues labelled `maintenance` (the empty text says only that none are recorded in those issues) with a `start:`/`end:` comment in the body, as Upptime documents. This repository has no incident or maintenance issues yet, so this parsing is untested against a real one. If the issues API cannot be read at build time, the page says the list was not available instead of saying there are none.
- Same-origin data: the page reads `./data/status.json` and `./incidents.atom` from its own origin. Those files only exist after a build step has produced them (see the proposal below).
- Language (EN/AR, RTL), light/dark/auto, reduced motion, keyboard use (the day bar takes arrow keys), strict meta CSP (`default-src 'none'`, scripts/styles/fonts/images/connect `'self'`). GitHub Pages cannot send headers, so `frame-ancestors` cannot be set. System fonts only.

## Publishing (proposal only)

`proposals/status-ui-build.yml` shows how a build could run after Uptime CI and Summary CI and publish `data/status.json` and `incidents.atom`. It would write to `gh-pages`, so it needs an explicit decision and a move into `.github/workflows/`. It is not part of this patch's behaviour.

## Quieter layout (revision)

The page shows less by default. The headline is one short title, one short count line and "Updated N ago". The methodology text lives in an (i) "About this page" panel, also reachable from the footer. Service rows show name, state, uptime and the 90 day bar. HTTP code, monitor-reported and check-count caveats, last recorded update and the response chart show only when a row is expanded. Range labels are 24 h, 7 d, 30 d and All. The "Sample data" banner appears only in fixture builds. Arabic follows the same structure.
